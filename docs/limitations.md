# 已知缺陷与边界

本文集中记录当前版本会影响协议保证、部署方式或运维的限制。这里列出的内容
是教学讨论题，也是评估是否适合具体场景的依据。MQTT 条目按
[一致性矩阵](conformance.md) 对照 MQTT 3.1.1；矩阵覆盖代表性要求，不是
正式符合性认证。

## 会改变消息交付结果的策略

| 限制 | 当前行为 | 影响 | 使用建议 |
|---|---|---|---|
| `max_inflight` 窗口满 | 跳过对该会话的 QoS 1/2 投递，在线与离线会话都可能发生；不结束会话 | 消息不会稍后排队重试，可靠交付保证被削弱 | 教学中设为 `0` 可关闭窗口限制；需要可靠投递时不要依赖该限额 |
| `max_memory` 内存压力 | 丢弃最旧的离线队列 QoS 1/2 消息，仍保留会话 | 持久会话消息可能丢失，且会话继续呈现为有效 | 为目标负载留足内存并监控丢弃计数；不要把策略当作 MQTT 合规行为 |
| `max_publish_rate` 超限 | PUBLISH 仍完成相应协议确认，但应用消息被丢弃；QoS 0 也会丢弃 | 客户端可能把已确认的消息视为成功，限流不提供延迟重试 | 视为 broker 的应用层丢弃策略；需要背压时在发送端实现 |
| `max_request_size` | 超过配置上限的包会被断开连接 | 合法但较大的 MQTT 3.1.1 包也可能被拒绝 | 根据业务 payload 调整上限，并考虑内存预算 |
| `$` 开头的客户端 PUBLISH | 被丢弃并完成协议确认；带 `$` 遗嘱的 CONNECT 被拒绝 | `$` 命名空间被保留给 broker 内部主题 `$SOL` | 客户端业务主题不要以 `$` 开头 |

其中 `max_inflight` 和 `max_memory` 的处理与持久会话保存 QoS 1/2 消息的
规范保证冲突：当前实现丢消息时没有结束会话。详细条款与测试见
[一致性矩阵](conformance.md) 的会话和资源策略章节。

## 会话与持久化边界

- 遗嘱属于连接状态，不写入快照或 WAL。broker 进程崩溃后，重启不会恢复旧连接的
  遗嘱并代为发布。
- 当前只有单 broker 进程的状态模型，没有集群复制、故障切换或多节点共享会话。
  多线程事件循环不等于分布式或高可用部署。
- `SIGHUP` 只重新打开日志文件，不重新读取配置。修改配置后需要重启 broker。

## 功能与安全边界

- 只实现 MQTT 3.1.1 的教学范围；MQTT 5.0、WebSocket 传输、桥接和共享订阅均未实现。
- 一致性矩阵列出代表性协议条目，不能据此声称服务器满足 MQTT 3.1.1 全部
  MUST 要求或通过正式一致性认证。
- 没有按 IP 统计失败认证次数的限额。公网部署还需要网络隔离、TLS、访问控制、
  日志监控和外围防护。
- `SIGHUP`、资源限额和连接配额是单机运维能力，不提供配置热更新、集群级配额或
  跨节点状态协调。

## 适用范围

本项目适合源码教学、协议实验和受控本机测试。若应用要求 QoS 消息不能因 broker
限额而静默丢失、遗嘱跨 broker 崩溃恢复、配置在线重载或多节点可用性，应先补齐
相应行为并增加独立客户端互操作测试，再评估部署。
