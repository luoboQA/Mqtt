# 设计取舍

这份文档记录“为什么是这样”，尤其是那些看起来可以更简单、但代价不同的地方。
每条都给出当时的约束、选择的方案、放弃的方案和可观测的代价。

## 1. 单进程 + 少量事件循环线程

**选择**：一个进程，`THREADSNR` 个事件循环线程，每个线程跑自己的
epoll/poll/select/kqueue，连接固定归属 accept 它的线程。没有线程池，没有
每请求任务队列。

**放弃**：thread-per-connection、leader-follower、异步回调框架。

**理由**：

- MQTT 连接是长连接、低单包开销，线程数随连接数线性增长不可接受。
- 连接归属固定，单个 client 的读写不需要锁；跨线程只发生在投递、踢连接、
  定时扫描，临界区小且明确。
- 调试和 TSan 可解释：共享状态只有 `server` 全局表和每 client 的少量原子字段。

**代价**：

- 一个慢客户端如果在内核发送缓冲满时阻塞，会拖住同 loop 的其它连接。当前
  写路径是非阻塞的（`EAGAIN` 后等 `EV_WRITE`），所以只在用户态拷贝上花时间。
- `THREADSNR` 是编译期常量，不能按 CPU 动态调整。
- 全局 `mutex` 在订阅/投递热路径上仍会竞争；连接数很大时是瓶颈。

## 2. 全局 `server` / `conf` 单例

**选择**：`extern struct server server; extern struct config *conf;`，所有模块
直接访问。

**放弃**：把 `server *` 作为参数穿过每一层，或依赖注入。

**理由**：原项目就是这种风格，改成显式传递会触及几乎所有函数签名；在单进程
单 broker 的假设下，单例没有语义损失。

**代价**：

- 单元测试必须先构造全局状态，纯模块（`mqtt.c`、`topic_match.c`）不得不
  绕开它们才能测。
- 同一进程内无法起两个 broker 实例（集成测试靠“一个测试一个进程”规避）。
- 生命周期靠 `main` 的调用顺序保证，没有 RAII/析构检查。

**后续**：完整重构会把 `server` 拆成 `struct sol` 上下文，handler 接收
`struct sol *`；`conf` 变成上下文里的只读字段。纯模块继续保持无依赖。

## 3. 主题索引：精确 Trie + 通配分段 Trie

**选择**：精确主题放 `Trie`（完整主题名为 key）；含 `+`/`#` 的订阅放另一棵
按 `/` 分段的树，发布时分别查两套索引，再按会话去重。

**放弃**：每次发布遍历所有订阅做字符串匹配；或只维护一棵“过滤器树”并在
发布时枚举所有匹配路径。

**理由**：

- 精确发布是绝大多数流量，Trie 查找 O(主题长度)，与订阅数无关。
- 通配订阅通常远少于精确订阅，单独索引避免让精确路径为通配付出代价。
- 分段树让 `+`/`#` 的匹配在结构上完成，不需要反复 `strtok`。

**代价**：

- 同一会话同时有 `a/#` 和 `a/b` 时，两条路径都能命中，必须在投递层去重
  （否则客户端收到两份）。去重按 `session_id` 做，见
  `deliver_retained()` / `publish_message()`。
- 退订 `a/#` 不能顺手删掉 `a` 的精确订阅，索引和会话订阅列表要同步维护。
- 空层（`a/`）和尾随 `/` 在 Trie 里是真实节点，不能做“去掉尾部斜杠”的
  归一化，否则 `a` 和 `a/` 会混为一谈。

## 4. 保留消息存“解包后的包”，不存原始字节

**选择**：`topic->retained` 是 `struct mqtt_packet *`，带引用计数；投递时按
订阅授予的 QoS 重新打包，分配新的 packet id。

**放弃**：把发布者收到的原始 PUBLISH 字节直接存下来重放。

**理由**：

- 同一份保留消息要投给不同 QoS 的订阅者，原始字节里的 QoS 和 packet id 是
  发布者的，不能复用。
- 引用计数让“发布者释放”和“订阅者持有”解耦，避免深拷贝整条消息。

**代价**：每次投递都要重新 pack，CPU 换内存；保留消息的 payload 在内存里
有一份解包副本。

## 5. 持久化：快照 + 每条 fsync 的 WAL

**选择**：`persistence_file` 指向快照，`<file>.wal` 是追加日志；每次状态变更
先写 WAL 并 `fsync`，到 `persistence_interval` 写整份快照并轮转 WAL。

**放弃**：只在退出时写快照；或引入 SQLite/LevelDB；或批量 fsync。

**理由**：

- 教学项目要能讲清“崩溃一致性”：快照给基线，WAL 给增量，generation 防重放。
- 每条 fsync 的语义最简单：进程被 `kill -9` 最多丢最后一条记录。
- 不引入外部依赖，格式可读、可迁移（v1 记录在加载时升级）。

**代价**：

- 写放大：每条消息一次磁盘同步，吞吐受限于 fsync。生产级 broker 会用
  批量提交或专用日志。
- 状态越大，快照越慢，且写快照期间会阻塞事件循环（当前是同步写）。
- 只覆盖“必须跨重启”的状态：遗嘱、在线连接、统计计数不落盘。

## 6. 内存超限时的三级降级

**选择**：超过 `max_memory` 时依次 (1) 回收无引用主题，(2) 丢最旧离线消息，
(3) 置 `over_memory` 拒绝新连接。

**放弃**：直接 OOM 退出；或对单连接做硬配额。

**理由**：

- broker 的可用性优先于个别离线消息的完整性；丢最旧的消息是 MQTT 允许的
  “服务器资源限制”行为。
- 拒绝新连接比让现有连接随机失败更容易观测和恢复。

**代价**：

- 离线消息可能静默丢失（有日志），客户端只能靠 QoS/应用层确认发现。
- 没有每会话 inflight 窗口上限，单个恶意会话可以占满大量内存，直到触发
  全局降级。这是后续要补的配额。

## 7. 协议严格性：畸形包直接断开

**选择**：固定头 flags、Remaining Length、字段长度、QoS 3、空主题、通配符
主题、CONNECT 前发别的包等，一律视为协议错误，记录日志并断开；有遗嘱则先
发布遗嘱。

**放弃**：尽量容错、忽略非法字段继续服务。

**理由**：

- v3.1.1 §4.8 要求协议错误关闭网络连接。
- 严格校验让 fuzz 的“崩溃”更容易被定义为失败，减少模糊地带。

**代价**：对实现有 bug 的客户端不宽容；调试时需要看 broker 日志才能知道
哪一条规则被触发。

## 8. 认证与 ACL

**选择**：`password_file` 每行 `username:hash`，`hash` 由 `passwd.py` 用
`crypt(3)` 生成；`check_passwd()` 用 `crypt_r()` 重算并比较。ACL 文件按
`user`/`client` 和主题树授权读、写、遗嘱。

**放弃**：明文密码、JWT、外部认证服务。

**理由**：无外部依赖，部署简单；ACL 文件可读，适合教学演示。

**代价**：

- `crypt(3)` 的强度取决于系统的 `crypt` 实现（通常是 SHA-512），不是专门
  的抗 GPU 哈希；后续计划支持 scrypt。
- 比较是否常数时间取决于 `strcmp`，理论上可计时；后续改成常数时间比较。
- 没有按 IP 的失败限流，暴力破解只能靠网络层防护。

## 9. 统计主题用 `$SOL` 而不是 `$SYS`

**选择**：broker 自己的统计发到 `$SOL/...`，并遵守 §4.7.2：以 `+`/`#` 开头
的订阅看不到 `$` 主题。

**理由**：避免和 Mosquitto 的 `$SYS` 语义混淆；同时演示保留主题、周期性
发布和保留通配符规则。

**代价**：通用监控工具默认订阅 `$SYS`，需要改配置；文档要写清楚。

## 10. 测试策略：纯模块优先

**选择**：把 §4.7 匹配抽成 `topic_match()`，把编解码留在 `mqtt.c`，让
`sol_proto_test` 不链接 server/event loop；集成测试用真实 socket 和真实
broker。

**放弃**：只做端到端测试；或为单测引入 mock 框架。

**理由**：

- 匹配规则和编解码是纯函数，表驱动测试最有效，也最适合 fuzz。
- 端到端测试覆盖并发、持久化、TLS 这些纯函数测不到的部分。

**代价**：两套测试的构建目标要各自维护源文件列表；新增模块时要同时考虑
“它属于哪套测试”。

## 11. 明确不做的事

- **MQTT 5**：属性、原因码、共享订阅会改变会话和投递模型，和当前“3.1.1
  教学实现”的目标冲突。
- **集群/桥接**：需要分布式会话、主题路由和冲突解决，超出单进程假设。
- **WebSocket**：传输层多一套握手和帧协议，对理解 MQTT 本身帮助有限。
- **每会话 inflight 窗口**：v3.1.1 没有 Receive Maximum，窗口大小是服务器
  策略；当前靠内存上限兜底，后续作为可配置项补上。
