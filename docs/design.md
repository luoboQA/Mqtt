# 设计取舍

这份文档记录“为什么是这样”，尤其是那些看起来可以更简单、但代价不同的地方。
每条都给出当时的约束、选择的方案、放弃的方案和可观测的代价。

## 1. 单进程 + 少量事件循环线程

**选择**：一个进程，`THREADSNR` 个事件循环线程，每个线程跑自己的
epoll/poll/select/kqueue，连接固定归属 accept 它的线程。没有线程池，没有
每请求任务队列。

**放弃**：thread-per-connection、leader-follower、异步回调框架。

**理由**：

- MQTT 连接是长连接、低单包开销，线程数随连接数线性增长不可接受。
- 连接归属固定，单个 client 的读写不需要锁；跨线程只发生在投递、踢连接、
  定时扫描，临界区小且明确。
- 调试和 TSan 可解释：broker 表归 `struct server` 持有；多个事件循环共享
  这些表，并由全局互斥锁和每 client 的状态保护。

**代价**：

- 一个慢客户端如果在内核发送缓冲满时阻塞，会拖住同 loop 的其它连接。当前
  写路径是非阻塞的（`EAGAIN` 后等 `EV_WRITE`），所以只在用户态拷贝上花时间。
- `THREADSNR` 是编译期常量，不能按 CPU 动态调整。
- 全局 `mutex` 在订阅/投递热路径上仍会竞争；连接数很大时是瓶颈。

## 2. 显式 broker 上下文

**选择**：`main()` 在栈上创建 `struct config` 和 `struct server`，并把配置地址
保存在 `server.conf`。连接、会话、I/O 事件和事件循环上下文都能沿着显式的
`struct server *` 找到所属 broker；配置 API 也显式接收 `struct config *`。

**放弃**：让业务模块依赖进程级 `server` / `conf` 单例。

**理由**：显式上下文让模块依赖和生命周期更容易走读，也让纯模块可以单独构建
和测试。它还把“状态属于哪个 broker”写进了数据流和函数签名。

**代价与边界**：

- `server` 和配置已不再是全局单例，但 `mutex`、统计计数、内存记账以及部分
  持久化/ACL 状态仍有进程级共享部分；当前程序仍按单 broker 进程设计，不能把
  多个实例当作彼此隔离的库对象使用。
- 生命周期由 `main()` 的调用顺序管理；C 没有析构检查，启动失败和清理路径仍
  需要按资源所有权逐项核对。

**模块约定**：服务器内部跨文件回调原型放在 `server_internal.h`；命令处理模块
之间共享的原型放在 `handlers_internal.h`。`mqtt.c`、`topic_match.c`、`util.c`
等协议和工具模块不依赖 broker 上下文。

## 3. 主题索引：精确 Trie + 通配分段 Trie

**选择**：精确主题放 `Trie`（完整主题名为 key）；含 `+`/`#` 的订阅放另一棵
按 `/` 分段的树，发布时分别查两套索引，再按会话去重。

**放弃**：每次发布遍历所有订阅做字符串匹配；或只维护一棵“过滤器树”并在
发布时枚举所有匹配路径。

**理由**：

- 精确发布是绝大多数流量，Trie 查找 O(主题长度)，与订阅数无关。
- 通配订阅通常远少于精确订阅，单独索引避免让精确路径为通配付出代价。
- 分段树让 `+`/`#` 的匹配在结构上完成，不需要反复 `strtok`。

**代价**：

- 同一会话同时有 `a/#` 和 `a/b` 时，两条路径都能命中，必须在投递层去重
  （否则客户端收到两份）。去重按 `session_id` 做，见
  `deliver_retained()` / `publish_message()`。
- 退订 `a/#` 不能顺手删掉 `a` 的精确订阅，索引和会话订阅列表要同步维护。
- 空层（`a/`）和尾随 `/` 在 Trie 里是真实节点，不能做“去掉尾部斜杠”的
  归一化，否则 `a` 和 `a/` 会混为一谈。

## 4. 保留消息存“解包后的包”，不存原始字节

**选择**：`topic->retained` 是 `struct mqtt_packet *`，带引用计数；投递时按
订阅授予的 QoS 重新打包，分配新的 packet id。

**放弃**：把发布者收到的原始 PUBLISH 字节直接存下来重放。

**理由**：

- 同一份保留消息要投给不同 QoS 的订阅者，原始字节里的 QoS 和 packet id 是
  发布者的，不能复用。
- 引用计数让“发布者释放”和“订阅者持有”解耦，避免深拷贝整条消息。

**代价**：每次投递都要重新 pack，CPU 换内存；保留消息的 payload 在内存里
有一份解包副本。

## 5. 持久化：快照 + 每条 fsync 的 WAL

**选择**：`persistence_file` 指向快照，`<file>.wal` 是追加日志；每次状态变更
先写 WAL 并 `fsync`，到 `persistence_interval` 写整份快照并轮转 WAL。

**放弃**：只在退出时写快照；或引入 SQLite/LevelDB；或批量 fsync。

**理由**：

- 教学项目要能讲清“崩溃一致性”：快照给基线，WAL 给增量，generation 防重放。
- 每条 fsync 的提交边界简单；崩溃时可能损失尚未完整落盘的最后一条记录。
- 不引入外部依赖，格式可读、可迁移（v1 记录在加载时升级）。

**代价**：

- 写放大：每条消息一次磁盘同步，吞吐受限于 fsync。生产级 broker 会用
  批量提交或专用日志。
- 状态越大，快照越慢，且写快照期间会阻塞事件循环（当前是同步写）。
- 遗嘱、在线连接和统计计数不落盘；遗嘱恢复边界见
  [已知限制](limitations.md)。

## 6. 内存超限时的三级降级

**选择**：超过 `max_memory` 时依次 (1) 回收无引用主题，(2) 丢最旧离线消息，
(3) 置 `over_memory` 拒绝新连接。

**放弃**：直接 OOM 退出；或对单连接做硬配额。

**理由**：

- broker 的可用性优先于个别离线消息的完整性；这是本项目的资源策略，不应
  讲成 MQTT 对 QoS 1/2 的常规保证。
- 拒绝新连接比让现有连接随机失败更容易观测和恢复。

**代价**：

- 离线消息可能静默丢失（有日志），客户端只能靠 QoS/应用层确认发现。
- 丢弃离线 QoS 1/2 消息后仍保留会话，会削弱持久会话的交付保证；细节见
  [已知限制](limitations.md)和[一致性矩阵](conformance.md)。
- 全局降级是最后一道闸门，它不区分“谁”在占用内存；更细的控制交给下面
  的每会话窗口和每 IP 连接数。

## 6.1 每会话 inflight 窗口与发布限流

**选择**：

- `max_inflight` 限制一个会话在途的 QoS 1/2 消息数，在线投递和离线队列
  共用这个计数；窗口满时该会话的新 QoS 1/2 投递被丢弃（有日志），入站
  PUBLISH 仍然被 ACK。
- `max_publish_rate` 用令牌桶限制单个客户端每秒的 PUBLISH 数，超出的包
  被丢弃，但 QoS 1/2 的确认照常返回。
- `max_connections_per_ip` 在 accept 后按对端地址计数，超限直接关闭。

**放弃**：让单个慢订阅者无限堆积、让发布者无上限刷包、或让一个地址耗尽
连接池。

**理由**：

- v3.1.1 没有 Receive Maximum，窗口大小只能由服务器决定；显式配额比等
  全局内存告警更可预测，也更容易和单个客户端对应。
- MQTT 没有“请慢一点”的协议消息，丢包但保持 ACK 是唯一不会让客户端
  无限重传的处理方式；QoS 0 本来就允许丢弃。
- 每 IP 连接数把“一个地址开几万条连接”这类最廉价的攻击挡在业务逻辑之外。

**代价**：

- 配额是静默丢消息（有 WARNING 日志），依赖应用的 QoS/业务确认发现。
- `max_inflight` 满时仍保留会话并丢弃新投递，会削弱 QoS 1/2 的交付保证；见
  [已知限制](limitations.md)。
- 令牌桶按客户端、按事件循环维护，多线程构建下每个连接仍只由一个循环
  处理，因此不需要额外锁；代价是限流精度到秒级而非严格平滑。
- `max_connections_per_ip` 只按地址计数，NAT 后的多个合法客户端会共享
  同一个配额，默认值 0（不限）保持兼容。

## 7. 协议严格性：畸形包直接断开

**选择**：固定头 flags、Remaining Length、字段长度、QoS 3、空主题、通配符
主题、CONNECT 前发别的包等，一律视为协议错误，记录日志并断开；有遗嘱则先
发布遗嘱。

**放弃**：尽量容错、忽略非法字段继续服务。

**理由**：

- v3.1.1 §4.8 要求协议错误关闭网络连接。
- 严格校验让 fuzz 的“崩溃”更容易被定义为失败，减少模糊地带。

**代价**：对实现有 bug 的客户端不宽容；调试时需要看 broker 日志才能知道
哪一条规则被触发。

## 8. 认证与 ACL

**选择**：`password_file` 每行 `username:hash`。`passwd.py` 默认生成
`$scrypt$N$r$p$salt$hash`（内存硬，抗 GPU/ASIC 离线爆破），`--crypt` 仍可
生成 `crypt(3)` 哈希以兼容已有文件和系统习惯；`check_passwd()` 两种格式都
认，比较用 `constant_time_eq()`。ACL 文件按 `user`/`client` 和主题树授权
读、写、遗嘱。`require_client_cert true` 在 TLS 上再要求一张由 `cafile`
签发的客户端证书（mTLS），握手阶段就拒绝无证书或链不可信的客户端。

**放弃**：明文密码、JWT、外部认证服务。

**理由**：无外部依赖，部署简单；ACL 文件可读，适合教学演示。scrypt 让
“拖走 password_file 离线爆破”的成本显著高于 SHA-512-crypt，而保留
`crypt(3)` 让迁移不需要一次性重写所有账号。

**代价**：

- scrypt 每次校验要几十毫秒和 16MB 内存，认证吞吐低于 `crypt(3)`；
  这是有意的取舍，连接建立不是热路径。
- 密码比较是常数时间，但用户名查找仍是哈希表查找，时序差异极小且不泄露
  密码本身。
- 没有按 IP 的失败认证限流，暴力破解仍主要靠 `max_connections_per_ip`
  和网络层防护；mTLS 可以把“有密码”降级为第二因素而非唯一因素。

## 9. 统计主题用 `$SOL` 而不是 `$SYS`

**选择**：broker 自己的统计发到 `$SOL/...`，并遵守 §4.7.2：以 `+`/`#` 开头
的订阅看不到 `$` 主题。

**理由**：避免和 Mosquitto 的 `$SYS` 语义混淆；同时演示保留主题、周期性
发布和保留通配符规则。

**代价**：通用监控工具默认订阅 `$SYS`，需要改配置；文档要写清楚。

## 10. 测试策略：纯模块优先

**选择**：把 §4.7 匹配抽成 `topic_match()`，把编解码留在 `mqtt.c`，让
`sol_proto_test` 不链接 server/event loop；集成测试用真实 socket 和真实
broker。

**放弃**：只做端到端测试；或为单测引入 mock 框架。

**理由**：

- 匹配规则和编解码是纯函数，表驱动测试最有效，也最适合 fuzz。
- 端到端测试覆盖并发、持久化、TLS 这些纯函数测不到的部分。

**代价**：两套测试的构建目标要各自维护源文件列表；新增模块时要同时考虑
“它属于哪套测试”。

## 11. 明确不做的事

- **MQTT 5**：属性、原因码、共享订阅会改变会话和投递模型，和当前“3.1.1
  教学实现”的目标冲突。
- **集群/桥接**：需要分布式会话、主题路由和冲突解决，超出单进程假设。
- **WebSocket**：传输层多一套握手和帧协议，对理解 MQTT 本身帮助有限。
